# TOPIC geometry: Exact geometric and temporal semantics of Waymo Perception v2 for 3D box projection and motion reporting (Stage 1)

## GEO-1 [high CRIT] Q1: definitions of global, vehicle, sensor, camera and image frames
CLAIM: Global is East-North-Up with z opposite gravity. Its origin is a remote point, not the segment start. Inference: treat world coordinates as meaningful only within one segment. Vehicle frame: x forward, y left, z up, origin on the ground at the rear-axle centre. Camera frame: origin at the lens centre, x out of the lens, y left, z up, right-handed. Image frame: +x along columns, +y along rows, origin at the top-left corner, and pixel 0 starts at the left edge of the first pixel.
EVID: Sun et al. section 3.2 defines all frames, and a vehicle pose maps vehicle to global. Pei Sun (Waymo) says the vehicle origin is the rear-axle centre and the global origin is remote (issue 119). Vincent Casser (collaborator) says the vehicle origin is on the ground (issue 597). The Motion-dataset thread (issue 490) says origins differ per scenario; the Perception statement is inferred from that. dataset.proto notes the pixel-0 convention.
SRC: https://arxiv.org/abs/1912.04838 ; https://github.com/waymo-research/waymo-open-dataset/issues/119 ; https://github.com/waymo-research/waymo-open-dataset/issues/597 ; https://github.com/waymo-research/waymo-open-dataset/issues/490 ; https://github.com/waymo-research/waymo-open-dataset/blob/master/src/waymo_open_dataset/dataset.proto
IMPACT: Depth is x_c, not z_c, so a textbook K[R|t] on the inverse extrinsic is wrong without an axis swap. SceneWindow should not expose raw world coordinates; use the vehicle frame or a window-local origin.
VERDICT: confirmed

## GEO-2 [high CRIT] Q1: extrinsic direction, intrinsics order, distortion model
CLAIM: [CameraCalibrationComponent].extrinsic.transform is camera-to-vehicle, row-major 4x4, so vehicle-to-camera needs its inverse. Intrinsics are stored as f_u, f_v, c_u, c_v, k1, k2, p1, p2, k3 with OpenCV-style radial and tangential coefficients. They apply to the stored scaled images, which keep their lens distortion, so distortion must be applied forward during projection and images must not be undistorted first.
EVID: dataset.proto and context.py both state camera to vehicle, and camera_model.cc composes it as vehicle_tfm_cam. An old proto comment said the reverse; Pei Sun corrected it in issue 24. The C++ variables k3, k4, k5 are OpenCV p1, p2, k3. The camera model outputs lens-distorted image coordinates.
SRC: https://github.com/waymo-research/waymo-open-dataset/blob/master/src/waymo_open_dataset/v2/perception/context.py ; https://github.com/waymo-research/waymo-open-dataset/blob/master/src/waymo_open_dataset/dataset.proto ; https://github.com/waymo-research/waymo-open-dataset/issues/24
IMPACT: Unit tests should pin this direction. Do not name anything vehicle_to_cam from the extrinsic column. Third-party snippets that skip distortion lose accuracy toward image edges.
VERDICT: confirmed

## GEO-3 [high CRIT] Q1: exact projection and treatment of points behind the camera
CLAIM: Waymo projects with u_n=-y/x and v_n=-z/x in the camera frame, applies the distortion polynomial, then scales by f and offsets by c. A point with x<=0 is invalid and returns u=v=-1, depth=-1. If the radial factor r_d leaves [0.8, 1.2] the result is invalid and coordinates are pushed along the ray to a radius of hypot(W,H). The ops call the model with bounds checking off, so valid=1 does NOT mean inside the image. I re-implemented the full model in NumPy and reproduced the constants in camera_model_test.cc, including t_h=-0.0272851 and u=94.114. OpenCV projectPoints matched the global-shutter formula to 3e-13 px under X_cv=(-y,-z,x).
EVID: camera_model.cc: CameraToImageWithDepth, DirectionToImage, ComputeDepthResidualAndJacobian, WorldToImageMovingPointWithDepth. camera_model_ops.cc passes check_image_bounds=false. The tutorial drops an object if any corner fails and notes that this is strict for partly visible objects.
SRC: https://github.com/waymo-research/waymo-open-dataset/blob/master/src/waymo_open_dataset/wdl_limited/camera/camera_model.cc ; https://github.com/waymo-research/waymo-open-dataset/blob/master/src/waymo_open_dataset/wdl_limited/camera/camera_model_test.cc ; https://github.com/waymo-research/waymo-open-dataset/blob/master/src/waymo_open_dataset/wdl_limited/camera/ops/camera_model_ops.cc
IMPACT: Full formula is in exact_reference. Add explicit in-image and x>0 checks. cv2.projectPoints has no r_d guard or behind-camera rejection, so filter first. Clip wireframe edges in camera space rather than dropping partly visible objects.
VERDICT: confirmed

## GEO-4 [high CRIT] Q1 and Q5: numeric precision trap
CLAIM: All geometry and timing must be float64. In float32 the epoch timestamps collapse to one value (spacing near 1.55e9 is 128 s), readout becomes negative, and rolling-shutter projection is silently disabled. My NumPy simulation shows the Waymo fixture then gives u=100.04 instead of 94.11 for a moving point. Inference: this explains the shifts reported in issues 255 and 271, and Waymo's float32 Python op test has expectations matching the collapsed behaviour.
EVID: Timestamps are doubles in seconds since epoch. Issue 146: float32 gave 5.58 px mean error against stored projections, float64 gave 1.43 px mean and 3.78 px max (FRONT, one frame, one user's measurement). Issue 255: a user reports float64 nearly eliminates the mismatch. camera_model_ops_test.py and the tutorial use tf.float32. The op kernels are registered for both float and double.

## TIME-3 [medium CRIT] Q5: rolling-shutter spread within one image
CLAIM: One real FRONT image gave trigger-to-done 54.25 ms with 9.99 ms shutter, so readout is about 44 ms (about 23 microseconds per column), and pose_timestamp was 4.3 ms after the mean of trigger and done. SceneWindow should carry this limit explicitly, and Stage 2 prompts should not treat absent boxes as clear space.
- Vehicle-frame positions are measured from the rear axle on the ground, not from the ego bumper, and Perception labels give no ego box. Raw x values overstate clearance to a leading or cut-in vehicle by the rear-axle-to-bumper distance, roughly 4 m for the Chrysler Pacifica named in issue 597 (my estimate, not a Waymo figure). Any clearance or gap reported in SceneWindow or IncidentReport needs a declared ego footprint and box-edge rather than box-centre distance.
- Box-centre jitter makes single-step differencing unreliable. In issue 137, consecutive 0.1 s world-frame steps give 7.37 and 8.51 m/s against a label of 7.97, about +/-0.6 m/s at 54 m range, while the 0.2 s central difference misses by only 0.034 m/s. Use a baseline of at least 0.2 s or a fit: Pei Sun suggests a constant-acceleration fit in that thread. Set any lateral-motion threshold for cut-in evidence above this noise, measured across a full segment.
- The official op needs its own environment. The PyPI wheel waymo-open-dataset-tf-2-12-0==1.6.7 is manylinux x86_64 only and pins tensorflow==2.13, numpy==1.23.5, pandas==1.5.3 and pyarrow==16.0.0, so it cannot run on an Apple Silicon Mac and should be isolated from the pipeline environment on PACE. Double kernels are present in source at tag v1.6.1, but GitHub has no v1.6.7 tag and I could not list the wheel's contents. Confirm the wdl_limited import path and float64 behaviour on PACE with the fixture before relying on it as an oracle.
- Stored pose time lags image centre in both samples available: 4.33 ms in the issue 544 image and about 5.5 ms against the principal-point time in the repo fixture. If this is typical, global-shutter projection with the stored image pose is exact near u=1150 rather than at the centre, and error is larger at the left edge than the right. Measure pose_timestamp minus the mean of trigger and done, and record rolling_shutter_direction, on the first segment; the TIME-3 and TIME-4 numbers depend on both.

=== 2. TRANSFORMS ===
T_w_vf = world_from_vehicle (use for all labels). T_w_vi = [CameraImageComponent].pose (per image). T_v_c = extrinsic (camera to vehicle).
p_world = T_w_vf * p_vehicle. Camera pose at image time: T_w_c = T_w_vi * T_v_c. Yaw in world: yaw_w = heading + atan2(T_w_vf[1,0], T_w_vf[0,0]).

=== 3. BOX CORNERS (box_utils ordering) ===
l=size.x, w=size.y, h=size.z, c=center, R=[[cos h,-sin h,0],[sin h,cos h,0],[0,0,1]] with h=heading.
Local corners, each multiplied by (l/2, w/2, h/2):
0(+,+,-) 1(-,+,-) 2(-,-,-) 3(+,-,-) 4(+,+,+) 5(-,+,+) 6(-,-,+) 7(+,-,+)
corner_vehicle = R * local + c.
Wireframe edges: (0,1)(1,2)(2,3)(3,0)(4,5)(5,6)(6,7)(7,4)(0,4)(1,5)(2,6)(3,7). Front face (+x, heading side): 0,3,7,4.

=== 4. GLOBAL-SHUTTER PROJECTION ===
Option A, image pose: p_c = inv(T_w_vi * T_v_c) * T_w_vf * p_v. Use for box on any camera.
Option B, extrinsic only: p_c = inv(T_v_c) * p_v. Waymo's tutorial path for camera_synced_box. Equal to A when frame pose equals image pose.
With p_c=(x,y,z):
if x <= 0: invalid (Waymo returns u=v=-1, depth=-1).
u_n = -y/x ; v_n = -z/x ; r2 = u_n^2 + v_n^2
r_d = 1 + k1*r2 + k2*r2^2 + k3*r2^3
if r_d < 0.8 or r_d > 1.2: invalid (Waymo returns u=c_u+u_n/sqrt(r2)*hypot(W,H), v likewise).
u_nd = u_n*r_d + 2*p1*u_n*v_n + p2*(r2 + 2*u_n^2)
v_nd = v_n*r_d + p1*(r2 + 2*v_n^2) + 2*p2*u_n*v_n
u = f_u*u_nd + c_u ; v = f_v*v_nd + c_v ; depth = x
In image only if 0 <= u < W and 0 <= v < H.
OpenCV equivalent: cv2.projectPoints on X=(-y,-z,x), rvec=tvec=0, K=[[f_u,0,c_u],[0,f_v,c_v],[0,0,1]], dist=(k1,k2,p1,p2,k3). Agreed to 3e-13 px on 175 random points. No guards, so filter x>0 first.

=== 5. ROLLING-SHUTTER PROJECTION (reference; see GEO-5 before porting) ===
Inputs: R_wv,t_wv from T_w_vi; R_vc,t_vc from T_v_c; v_w=linear_velocity; omega_v=angular_velocity (vehicle frame in code); t_p=pose_timestamp; s=shutter; t_tr, t_d; W,H; direction d.
readout r = t_d - t_tr - s
pixel time tau(x,y) = t_tr + s/2 + r*q, q = y/H (TOP_TO_BOTTOM), (H-y)/H (BOTTOM_TO_TOP), x/W (LEFT_TO_RIGHT), (W-x)/W (RIGHT_TO_LEFT)
t_off = t_p - tau(c_u, c_v)
horizontal = d in {LEFT_TO_RIGHT, RIGHT_TO_LEFT}
A = u_n(W,H/2) - u_n(0,H/2) if horizontal else v_n(W/2,H) - v_n(W/2,0), using undistorted normalised coordinates
F = r/A, negated for RIGHT_TO_LEFT or BOTTOM_TO_TOP
R_cw0 = (R_wv*R_vc)^T ; c_w0 = R_wv*t_vc + t_wv
S = skew(R_vc^T*omega_v) ; omega_w = R_wv*omega_v ; v_c = v_w + skew(omega_w)*(R_wv*t_vc)
For t = t_capture - t_p, object world velocity v_o (zero for plain WorldToImage), point p_w valid at t_p:
R_cw(t) = (I - t*S)*R_cw0 ; c_w(t) = c_w0 + t*v_c
P = R_cw(t)*(p_w + t*v_o - c_w(t)). If P_x <= 0: invalid.
u_n=-P_y/P_x ; v_n=-P_z/P_x ; n = u_n if horizontal else v_n
e = t - n*F + t_off
L = R_cw(t)*(v_o - v_c) - S*P
J = 1 - F/P_x*(u_n*L_x - L_y) if horizontal else 1 - F/P_x*(v_n*L_x - L_z)
Newton from t=0: t = t - e/J until |e| <= 1e-5 s, at most 4 iterations. Reject if |e| > 0.1 s. Then apply section 4 distortion to the final u_n,v_n.
Official op input: extrinsic [4,4], intrinsic [9], metadata int32 [W,H,direction], camera_image_metadata [26] = pose(16)+v_xyz(3)+w_xyz(3)+pose_timestamp+shutter+trigger+done, global points [N,3]. Output [N,3]: u, v, valid. All tf.float64 except metadata.

=== 6. STAGE 1 RECIPE ===

=== 7. MOTION CONVERSIONS ===
R = T_w_vf[:3,:3]. v_obj_w = (speed.x, speed.y, 0) ; v_ego_w = FRONT linear_velocity, or (t_w[k+1]-t_w[k-1])/(ts[k+1]-ts[k-1]) with ts in seconds.
Absolute velocity in ego axes: R^T*v_obj_w. Relative velocity in ego axes: R^T*(v_obj_w - v_ego_w). Ego speed: |v_ego_w|. Longitudinal and lateral ego components: first two entries of R^T*v_ego_w. Object along-heading speed: v_obj_w dot (cos yaw_w, sin yaw_w, 0).
Trajectory test: p_w[k]=T_w_vf[k]*center[k]; v_hat[k]=(p_w[k+1]-p_w[k-1])/(ts[k+1]-ts[k-1]). Compare with speed under: global axes; rotated to ego axes; ego-relative; raw vehicle-frame difference. Expect global to win by a wide margin. Public sample residuals: 0.034, 12.3, 9.1, 8.3 m/s.
